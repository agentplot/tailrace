# The registry store checks a tag before and after its put and takes the host's Docker credentials

Deciders: proposed by the-registry-store unit of phase 1's bolt 3, which binds the store seam to an OCI registry and proves it against zot, the reference distribution and a real ECR repository (`agentplot/blueprints:design/tailrace/models/phase-1-bolts.md`, Bolt 3), with the read again after a put, what a resolve answers after a move, and what a move from a place the name has left rests on ruled by madswan-design, for the user to accept with the change.
Sources: statement clauses 22, 33, 36, 54, 59, 61, 64, 70, 71, 87, 105, 109, 120, C.1 as amended at `agentplot/blueprints` 62283d9, b96697a and 8dd5cc8; ADRs 0003, 0014; rules core.4, core.6, core.15, core.19, core.20, core.21, core.38; the OCI distribution specification (main), its sections on pushing manifests and on the referrers API; aws/containers-roadmap issues 2306 and 2783; the change's design, D4, D7, D9, D13 and D15; nine runs of the store's conformance group against ECR, three before name read a tag again, three after, and three after the group read a moved name until it settled, and reads by hand against the same registry, in us-west-2 on 2026-10-25.

## Context and problem statement

ADR 0014 settled where the registry store holds what it holds: one declared repository, attestations typed by tailrace's envelope type with the predicate type annotated, and a cache entry's bytes named through a cache manifest. Four questions were left to the profile.

C.1 has a name moved "with the expected digest where the registry supports it and checked after the move where it does not". The distribution specification defines no conditional request for a tag put, and no registry this change binds honours one, so a tag put cannot be refused for being somewhere other than where the caller expects it. How does name keep a move from anywhere but the expected digest refused and a refused move reported, never retried (70, core.6)?

ECR does not always show a put at once. In three runs of the store's conformance group against an ECR repository, one in three failed the same way: ECR took the tag's put, and the store's read back straight after it answered the manifest the tag was at before, so name refused its own move as a lost race. By hand, in one round of three, six reads over ten seconds after a tag's move all answered its former manifest; in six further rounds every read answered the new one. How does name tell a registry not yet showing its put from a race another writer won, without putting the tag again?

ECR's tag reads are not monotonic either. In three further runs, with name reading a tag again while it answered the former place, one in three failed the same scenario a step later: name's read again answered the new manifest, so name answered the move made, and the scenario's next resolve of the name, straight after, answered the manifest it was moved from. What does a resolve on a registry answer after a move, and what does name take as its put shown?

A tag read before the put lags as a read after it does. In three runs more, with the group reading a moved name until it settled, one in three failed the cache manifest's scenarios: a name moved from one entry's bytes to another's and read settled at the other was asked to move from the first bytes, a place it had left; name's check before the put read the tag, ECR answered the place the name had left, the check passed, and the put went through, with no word from ECR. No registry this change binds takes a condition on a tag put, ECR among them. What does a move from a place the name has left rest on, and what does the conformance suite ask of a profile whose names take no condition?

ECR asks every request for a credential, and zot or Harbor ask where the operator sets them to. tailrace keeps no credential; one is the asker's, the host's or the environment's, reached at the moment of use (64, core.21). Where does the profile find one, and what does it keep?

ECR announced support for OCI 1.1 in 2024, and two issues open against it say otherwise: 2306, a manifest whose artifact type or layer media type carries a parameter refused 405 `UNSUPPORTED` "Invalid JSON syntax", and 2783, an OCI 1.1 referrer manifest refused with the same words. Neither says what in the manifest ECR objects to, so only a push answers whether ECR takes the forms the profile writes.

## Considered options

For a name:

1. Read the tag and refuse unless it is at the expected digest, put it, and read it back; a tag found at another digest after the put is a lost race, refused naming that digest, with nothing retried.
2. A conditional put on the tag's `ETag` where a registry answers one, and option 1 elsewhere.
3. A lock the store takes before a move, held in a tag or a ref of its own.
4. No registry bound that cannot refuse a tag put conditionally.

For a read back that answers the place the tag was moved from:

1. Read again at growing intervals while the tag answers the former place, for at most a bound the profile names: the new digest is the move made, a third digest a lost race, and the bound passing a refusal naming the former place, with the put never repeated.
2. The move answered made when the read back answers the former place, with no read again; only a third digest is a lost race.
3. One read back, every digest but the new one a lost race.

For a resolve after a move:

1. A resolve is the answer as of when it read (36): it may answer a place the name was at for up to the profile's bound after the move, settling on the new digest within it and never answering a digest the name was never at; name takes one read of the new digest as its put shown; and the conformance suite reads a moved name until it settles or the bound the profile declares passes.
2. name reads the tag again until it answers the new digest several times running, and only then answers the move made.
3. resolve reads the tag again until the bound passes, answering only what the last reads agreed on.

For a move from a place the name has left, on a registry whose tag put takes no condition:

1. The check before the put kept as best effort, and nothing of a move's safety resting on it: the profile declares that its names take no condition, and the conformance suite runs, in place of its refusal of a move from where the name is not, a move from a place the name has left with either answer taken, and the name then repaired from the ledger to where its head says.
2. The check read again while it answers the expected place, up to the bound, before the put.
3. The refusal kept as a scenario of the suite on every profile.

For the credential:

1. The host's Docker configuration, through `docker_credential`: its `auths`, `credsStore` and `credHelpers`, ECR's `ecr-login` helper among those it runs, read when the registry's challenge asks for a credential.
2. The AWS SDK's authorization token for an ECR host, and the Docker configuration for every other.
3. A credential named in the bindings file or kept in tailrace's state.
4. A login run before the store is used, `docker login` or `crane auth login`, as a subprocess.

## Decision outcome

A name is option 1. name reads the tag and refuses a move from anywhere but the expected digest, as far as that read shows, naming where the tag is; puts the manifest the digest names, or the cache manifest of bytes it names, under the tag; and reads the tag back, refusing naming what it found when that is a digest neither asked for nor the one the tag was moved from (70, 71). Nothing is retried after either refusal (core.6). The read back cannot close the window between the check and the put: two writers can each pass the check and each read back their own put when their puts and reads interleave, and the store cannot see it. That window is harmless for every name tailrace moves. A channel's name moves only by the gate, after the keeper took its promotion at the chain's head, which two promotions cannot both do (105, 120), and a race lost on it is repaired from the ledger by the core, which moves the name once from where it was found to the digest the head is about (109, design D9). A version's name is claimed in the shared history before anything is packed (22), so two publishers never reach the store with one version. A cache entry's name is at the bytes the build identity names, whoever writes it. The profile exposes one hook for the tests, run between the put and the read back and hidden from the docs, so the tools layer loses a race on purpose. Option 2 is a branch on a header no registry this change binds sends, code no test would run; it is a change to name alone when one does, and C.1 already allows it. Option 3 is state tailrace keeps beside the store (61, core.20) and binds no writer that does not take it, a person moving a tag with another tool among them. Option 4 binds no registry.

The read back is option 1, with one bound for every registry the profile binds, 30 seconds (C.1). The first read again waits a quarter of a second and each later one twice as long as the one before, so the tag is read at about 0.25, 0.75, 1.75, 3.75, 7.75 and 15.75 seconds after the put and once more as the bound passes. A registry that shows its put at once answers the first read back and never waits; ECR, which answered a former digest for over ten seconds, is given three times that. A tag found at the new digest is the move made; at any third digest, the race another writer won, refused naming that digest at once (109); still at the former place when the bound passes, refused naming the former place, in words saying the registry still answered it there that long after the put and that nothing was put again. core.6 holds because nothing is retried: the put was answered as taken, and reading the tag again asks the registry what that one put did, moving nothing; the put is never repeated, and a refusal, either of the two, is reported. Option 2 answers a move made that the store never saw, and a writer moving the name back to the former place between the put and the read back goes unseen. Option 3 refuses on ECR, about one run in three, a move ECR took, so the store reports races no one ran and ECR cannot be proven.

A resolve after a move is option 1 (C.1 as amended at `agentplot/blueprints` b96697a). The registry is read where it answers, and no read of it promises the answer the next read gives; a reader that holds an older answer holds it as of when it read (36). A stale resolve costs no correctness: nothing of tailrace acts on a resolve where the ledger holds the answer, since a promotion is written to the ledger before its channel's tag moves and a channel's head is read from the chain (33, core.4, core.15), and a version's name and a cache entry's name are each at one digest whoever writes them. name's read again stays as it is: one read of the new digest is the put taken, and a later stale read contradicts nothing the put did. The profile declares its bound, 30 seconds, to the conformance suite, and the suite's store group reads a moved name until it answers where the name was moved, again while it answers a place the name was at until that bound passes, and fails at once on a digest the name was never at; the layout store and the fakes declare no bound and answer at once. The cache manifest's scenarios read a moved name the same way. Option 2 waits longer and promises no more, since no number of reads stops the next from answering a former place. Option 3 makes every resolve wait out the bound, a name long settled among them, since a resolve cannot tell a moved name from one at rest.

A move from a place the name has left is option 1 (C.1 as amended at `agentplot/blueprints` 8dd5cc8). A move by expected digest cannot hold on a registry whose tag put takes no condition, and no read before the put stands in for one: the check is a read a lagging replica defeats, so its refusal is best effort, and name keeps it as that. A move's safety rests where the statement already puts it. The ledger is written before a channel's name moves (33), and the chain admits one successor to a head (105), so one party moves a channel's name at a time; a name found elsewhere is repaired from the ledger, the core moving it once from where it was found to the digest the head is about (109, design D9). A cache entry's name is made once from nothing at bytes every writer of its build identity agrees on (87), and a version's name is claimed in the shared history before anything is packed (22), so neither is moved from a place it has left. The registry declares that its names take no condition on every registry it binds, zot and the reference distribution among them, whose tag puts take none either; the layout store and the fakes declare that theirs do, the layout's check and move made under its index's lock. The store group's refusal of a move from where the name is not runs on a profile whose names are conditional. On one whose names are not, the group moves a name from a place it has left, takes either answer, the move made or a refusal naming a place the name was at, and repairs the name from a ledger whose head is about where it was, which must put it there; each of the two is not applicable on the other kind of profile. The cache manifest's scenarios, which the run against ECR pushes, move no name from a place it has left; the check's refusal of one, a cache entry's naming the bytes' digest and never the cache manifest's, is proven on zot and the reference distribution, where every read shows a move at once. Option 2 narrows the window and does not close it: a replica that lagged on one read can lag on the next, and the put still goes through. Option 3 asks ECR for what its tag put cannot keep, so ECR is never proven.

The credential is option 1. A request goes unauthenticated first, so a registry that asks for nothing is sent nothing. On a 401 the profile reads the `WWW-Authenticate` challenge and asks `docker_credential` for the host's credential for the registry host at that moment: for `Basic` it sends it; for `Bearer` it asks the challenge's realm for a token for the scope the challenge names, with the user and password as `Basic` or an identity token as a refresh grant, and sends the request once more with the token. What authorizes the next request is held in memory by the one handle for the life of the process and written nowhere (64, core.21). A host with no credential for the registry gets the challenge as the answer, refused in the registry's words and naming it (59, core.19); a helper that fails is unreadable in its own words. The bindings file names the repository and never a credential. One path serves every registry and the setup the operator already has for docker, crane and oras, and ECR through its helper, which reads `AWS_PROFILE` from the environment. Option 2 names one registry's SDK in the profile and brings a second dependency tree for what ECR's helper already does. Option 3 is what 64 and core.21 rule out. Option 4 is a further pinned tool whose login leaves the credential where the next run finds it, a store tailrace would have written.

## What ECR answered

The store's conformance group and the cache manifest's scenarios ran three times against the repository `tailrace-tools`, its tags mutable, in us-west-2 on 2026-10-25, by hand with a live session (`moon run ':#check-ecr'`, design D15), before name read a tag again; one run in three failed on the lag above, and no run was refused a form. They ran three times more with name reading a tag again, between 19:11 and 19:13 UTC the same day: two passed, and one failed the store group's scenario of a name moved from where it is not on the next resolve after the move, with no word from ECR and nothing refused, before the group read a moved name until it settled. They ran three times more with the group reading a moved name until it settled, at 19:22:52, 19:23:22 and 19:23:52 UTC the same day: two passed, and the third failed the cache manifest's scenarios on a move from bytes the name had left, which ECR took, with no word from ECR and nothing refused, before the suite took a move from a place the name has left as best effort; the repository holds that run's tag where the move put it. The forms the store sends no store operation of, and the referrers API's two headers, were read by hand with oras 1.3.3 against the same registry on the same day, the immutable tag in a second repository, `tailrace-tools-immutable`. The account is named in none of the words below.

### Consequences

- A name on a registry can lose a race the check before the put cannot see. The read back sees it, refused naming the other writer's digest, and for a channel the core repairs it from the ledger.
- A move on ECR may take up to 30 seconds longer to answer while ECR shows the put; on a registry that shows it at once it takes no longer. A tag still at the former place when the bound passes is refused naming that place, and for a channel's name the core's repair reads that refusal as it reads any naming where the name was found (109, design D9).
- A resolve on ECR may answer a moved name's former place for up to 30 seconds after name answered the move made. Nothing of tailrace acts on such a resolve where the ledger holds the answer (33, core.15); a test, or a person, reading a name just moved reads it until it settles.
- The check before the put can read a place the name has left, and a move from there then goes through, on ECR and on any registry whose tag put takes no condition. Nothing rests on the check: a channel's name is moved by one party at a time and repaired from the ledger where it is found elsewhere (33, 105, 109), and a cache entry's or a version's name is never moved from a place it has left (22, 87). The store group's report over the registry names its refusal of such a move not applicable, and the repair from the ledger run in its stead.
- When a registry this family binds answers a conditional tag put, the expected digest goes with the put there, a change to name alone.
- A host binds a registry by naming its repository; its operator sets up the Docker credentials once, as for any client of that registry, and for ECR maps the registry host to `ecr-login` in `credHelpers` with the `AWS_PROFILE` the helper reads in the environment.
- A repository with immutable tags keeps a name where it was made and refuses its move in ECR's words, so a store whose channels move needs mutable tags.
- A lifecycle rule expiring untagged images leaves an artifact a tagged index names, by ECR's own preview, and takes a manifest no tag and no tagged index reaches; what it does to a referrer, whose subject a tag reaches, the preview did not read.
- ECR is proven by the runs this record names and by no run of the gate, which holds no person's session (core.38); a later change to the forms `oci.rs` writes, or to how name reads a tag, is proven against ECR again by hand.
