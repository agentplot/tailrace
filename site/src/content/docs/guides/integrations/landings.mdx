A landing is the event by which a revision reaches a branch through the
repository's own gate, sluice or its like, which is not tailrace's gate.
tailrace publishes only landed revisions, and reads exactly one landing
(92). The landing does not know tailrace exists.

## The contract

The seam is two operations (77, 78). **landed** takes a branch and a
revision and answers whether the branch has landed it. **verdicts-of**
takes a revision and answers every signed verdict the landing recorded
for it, each naming its check, its build identity, its outcome and its
signer, as the landing recorded them. A publish refuses a revision the
landing has not landed before anything is read or offered, and where the
landing has verdicts, offers only outputs whose build identity a verdict
names.

## Members

| member | profile | how | status |
|---|---|---|---|
| sluice | C.5 | a revision is landed when sluice's log for the branch holds its landing; verdicts are the signed results under `refs/sluice/runs/<signer>` for the combination that landed it, each an in-toto statement in a DSSE envelope with the test's key and system as its subject and moon's hash as its digest; a result sluice replayed is carried as the signed pass that ran on the same key and system, and every envelope is carried whole, each signature with its key id, as sluice wrote it | built |
| a plain git branch | C.6 | where sluice does not run a branch, a revision is landed when the branch's history contains it, and there are no verdicts | built |

The landing is bound for a host by its bindings file (see
[self-hosting](/tailrace/guides/self-hosting/)): `[landing] sluice = {
remote = "origin" }` or `branch = { remote = "origin" }`, the remote
optional. With a remote, sluice's records or the branches are read from
it; without one, from the repository's own refs and files.

## Read as last fetched

With a remote bound, the landing is read on the remote, and each read
fetches what it reads into the host's copy (60, 77). Where the remote
does not answer, the landing answers from that copy as last fetched,
saying when it was fetched and carrying the remote's own words of why it
did not answer, never a refusal and never a guess (59, 61). Status names
it under the branch's head, `landing: as last fetched` with the time in
UTC and the remote's words beneath, on the command line, in its JSON and
on the host's page.

A yes from the copy is a yes: a branch only moves forward, so a revision
it held when fetched it holds now. A no from the copy is refused as not
landed as last fetched, naming the branch, the revision and when the
copy was fetched, with the remote's words, and saying to ask again once
the remote answers; a program tells it apart by
`refused.why.not_landed_as_fetched` in the JSON. tailrace never asks
again by itself. A question the copy cannot answer, because nothing of
it was ever fetched, is unreadable with the remote's words.

The copy is tailrace's own refs in the repository, beside its own and
never in place of them: `refs/tailrace/landing/heads/<branch>` for a
plain branch, and `refs/tailrace/landing/sluice/state/<branch>` and
`refs/tailrace/landing/sluice/runs/<signer>` for sluice, remade at each
fetch so each ref's reflog says when. No remote-tracking ref,
`FETCH_HEAD` or branch is written. Any git reader sees the copy with no
tailrace process running, and the next read that reaches the remote
makes it again (62, 63).

## Adding one

A landing profile implements the one landing interface and nothing of
the core, and is bound for a host by the operator (92). It passes the
one conformance suite, which holds it to Parts A and B; a profile that
fails the suite is not one (93).
